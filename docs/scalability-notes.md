# 확장성 노트

현재는 한 학교(1개 캠퍼스) 규모를 전제로 한 구성이다. 트래픽이나 도입 학교가 늘어날 때
어디가 먼저 병목이 되고 어떻게 대응할지를 정리한다.

## 현재 구성과 한계
| 영역 | 현재 | 먼저 한계가 오는 지점 |
|---|---|---|
| 애플리케이션 | Cloud Run 3개 서비스(backend/ai/frontend), 요청이 없으면 0대까지 축소 | `--max-instances`(backend 2, ai 1, frontend 2)로 상한을 걸어둠 |
| DB | Supabase(PostgreSQL + pgvector), Session pooler 경유 | 동시 커넥션 수: 인스턴스당 풀 최대 5 × 인스턴스 수 |
| AI | Gemini API (의도분류: Flash-Lite) | API 쿼터·비용, 응답 지연 |
| 배치 | Cloud Scheduler → HTTP 엔드포인트 | 신고 데이터가 많아지면 탐지·예측 계산 시간 |

## 트래픽이 늘면
1. **Cloud Run 인스턴스 상한 상향** — 배포 설정의 `--max-instances`만 바꾸면 자동 확장. 단, DB 커넥션 합계가 풀 한도를 넘지 않도록 인스턴스당 풀 크기(`app/db/session.py`)와 함께 조정
2. **DB 커넥션** — Session pooler → Transaction pooler 전환 또는 Supabase 유료 플랜으로 커넥션 한도 확대
3. **AI 비용·지연**
   - 반복되는 행정문의는 RAG 결과를 캐싱해 Gemini 호출 자체를 줄임 (명세서 11장 결정: 인메모리 캐시로 시작, 인스턴스가 여러 대가 되면 공유 캐시 필요)
   - 의도분류처럼 단순한 작업은 가장 저렴한 모델, 답변 생성만 상위 모델 — 모델을 환경변수로 분리해둠
4. **벡터 검색** — 임베딩 768차원 + HNSW 인덱스라 문서 수가 수만 건 수준까지는 인덱스만으로 대응 가능
5. **콜드스타트** — 트래픽이 꾸준해지면 최소 인스턴스를 1 이상으로 설정해 첫 응답 지연 제거

## 다른 학교로 확장하면
- 학교마다 다른 값(카테고리, 우선순위 매트릭스, SLA 시간, 탐지 기준)은 코드가 아니라 **설정 테이블**에
  있어서 데이터만 바꾸면 된다 (명세서 5장, 11장 "학교별 확장성")
- 완전한 멀티테넌트(학교별 데이터 격리·로그인)는 현재 범위 밖. 필요해지면 테이블에 학교 ID를
  추가하고 RLS 정책으로 격리하는 방식이 자연스러움 (이미 전 테이블 RLS가 켜져 있음, ADR 0006)

## 운영 안정성
- 배포는 리비전 단위라 문제 시 직전 리비전으로 즉시 롤백 (runbook)
- 테스트·시크릿 검사 실패 시 배포 자동 차단, 라이브러리 버전 고정 (ADR 0007)
