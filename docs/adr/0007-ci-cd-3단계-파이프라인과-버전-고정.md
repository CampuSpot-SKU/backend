# ADR 0007: CI/CD를 test ∥ build → deploy 3단계로, 라이브러리 버전은 전부 고정

## 상태
확정 (2026-09-28)

## 문제
초기 워크플로우는 레포마다 구조가 달랐고(ai는 `ci.yml`·`deploy.yml`이 따로 동시 실행),
lint 실패를 무시(`|| true`)해서 **테스트가 실패해도 배포가 진행**됐다. 또 Python·npm
라이브러리 버전을 고정하지 않아, 코드를 바꾸지 않아도 새 버전 출시로 배포가 깨질 수 있었다
(실제로 DB 드라이버 불일치로 배포가 실패한 적 있음 — runbook 참고).

## 결정
- 세 레포 모두 워크플로우 파일 1개(`deploy.yml`), job 3개:
  - `test`(gitleaks 시크릿 검사 + lint/타입체크/테스트)와 `build`(Docker 이미지 빌드·push)는 **동시에** 실행
  - `deploy`는 `needs: [test, build]` — 둘 다 성공해야 실행. backend는 배포 직전 `alembic upgrade head`
  - PR에서는 `test`만 실행
- `concurrency`로 연속 push 시 배포가 겹치지 않고 순서대로 실행
- 이미지 태그는 커밋 SHA만 사용(`latest` 안 씀) → 어떤 커밋이 배포됐는지 정확히 추적·롤백
- Cloud Run `--max-instances`로 과금 폭주·Supabase 커넥션 고갈 방지 (backend 2, ai 1, frontend 2)
- 러너는 `ubuntu-24.04` 고정, 액션은 Node 24 버전
- 버전 고정: backend `requirements.txt`(`==`), ai `pyproject.toml`(`==`, 의존성 목록 단일화),
  frontend `package-lock.json` + `npm ci`

## 검토한 대안
- 2단계(test → build+deploy): 구조는 더 단순하지만 배포만 실패했을 때 재빌드가 필요
- 순차 3단계(test → build → deploy): 단계가 늘어난 만큼 전체 시간 증가

## 트레이드오프
- 테스트가 실패해도 이미지는 만들어짐(배포는 안 됨) → 저장 공간 약간 낭비
- 라이브러리를 올리려면 숫자를 직접 바꿔야 함 → 의도하지 않은 업데이트를 막는 게 목적이라 감수

## 왜 이렇게 결정했는지
test와 build를 병렬로 돌려 단계를 나눠도 시간이 늘지 않으면서, "배포만 재실행"과
"테스트 실패 시 배포 차단"을 모두 얻는다. 데모 직전 깨진 코드가 자동 배포되는 위험과,
라이브러리 업데이트로 인한 돌발 장애를 구조적으로 막는 것이 5.5주 일정에서 가장 큰 리스크 관리다.
